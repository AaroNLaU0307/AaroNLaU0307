# Audit: semiconductor-yield-screening (UCI SECOM yield screening)

## Scope and method

- Commit audited: `d64e64486df7f75b4ce7ec0883ed5a331d19c43d` (HEAD, 14 commits, all dated 2026-08-23). The audited repo was read-only; nothing in it was modified (`git status` clean after the audit).
- What I ran: a local Python 3.11 venv with a fresh unpinned install (numpy 2.4.6, pandas 3.0.6, scipy 1.17.1, scikit-learn 1.9.1, duckdb 1.5.5, plotly 7.1.0, statsmodels 0.15.0). In a scratch clone I ran: the checksum check (all 3 files match `data/raw/CHECKSUMS.json`), `pytest --collect-only` (51 tests), the fast suite (50 passed, 13 s), the slow determinism test (passed, 148 s), and `run_pipeline.py`, `run_data_qa.py`, `build_doe_proposal.py`, `build_dashboard.py`. I then diffed every regenerated artifact against the committed one. I also ran `ruff`, the em-dash guard, git-history and blob-size checks, and a grep for secrets, absolute paths and bare excepts.
- Auditor spot checks (auditor-local scripts, not committed): pure-noise FDR rate, the D3 missing-rate band table, the D2 dedup count, a circular-shift label null on the train screen, within-holdout time trends for the two "replicating" sensors, a week-centred holdout effect, and the time-trend base rate for selected vs non-selected features. These are diagnostics only. None of them replaces a reported number.
- Not verified: live GitHub Actions status (badge); whether the committed raw bytes equal the current UCI archive (no downloads were allowed, and no source URL or retrieval date is recorded); the UCI licence text (stated from auditor knowledge as CC BY 4.0); the README claim that the dashboard "issues exactly one network request" (no browser); regeneration of `docs/*.png` (matplotlib, kaleido and pillow are not in requirements, so not run).

The 0.56/0.57 figure belongs to sensor_510 (0.5647, reports/replication.md:60). The error sits in the paragraph that claims to "exclude" sampling bias — fix it to "+0.22 to +0.53" and generate this sentence from `dashboard/replication_data.json` (S).
- [P0] (factual) The generated SPC report claims the holdout OOC rate is higher than the train rate "for every charted sensor", which its own table contradicts — reports/spc.md:123 (hard-coded prose at scripts/run_pipeline.py:666-667) versus reports/spc.md:24 (sensor_103: train 0.3878, holdout 0.3715). The false claim is reused as corroborating evidence for drift at DECISIONS.md:629-630 ("elevated holdout out of control rates ... independently support") and in the dashboard caption at scripts/build_dashboard.py:63 ("more common after it") — compute the statement from the table (the correct version is "9 of 10") (S).
- [P0] (factual) The DOE proposal and the README "3 candidates" target the sensors that the project's own replication analysis discredits — reports/doe_proposal.md:13-17 (factors sensor_059, sensor_477, sensor_205, chosen as the top 3 train effects at scripts/build_doe_proposal.py:84-87) and README.md:291-295 ("buying that evidence for 3 candidates"). Against this, README.md:35-37 calls sensor_059 the "clearest case" of a time artifact (holdout effect -0.05), sensors 477 and 205 have holdout effects of +0.03 and +0.02 (reports/replication.md:99-101), and README.md:66-67 names sensor_103 and sensor_510 as "the two candidates worth a process engineer's time". The headline experiment and its 1346-lot cost are built around discredited sensors — regenerate the DOE for the two replicating sensors, or state explicitly why the train top 3 were kept, and fix "3 candidates" (S).

**P1**

- [P1] The "decisive" permutation null assumes labels are exchangeable across time, which the repo itself rejects — yield_screening/screening.py:332-336 (iid permutation via argsort of uniform noise) versus DECISIONS.md:45-47 ("not exchangeable across time"). README.md:13-17 calls it "decisive ... p = 0.0005", and DECISIONS.md:260-266 calls it "the one result that cannot be argued with". Auditor spot check on the same train matrix, using a circular-shift null (1095 shifts, which preserves the label autocorrelation; label vs time Spearman on train = -0.18, p = 3e-9): null mean 7.6 (iid: 0.25), p95 27, max 53, share with zero survivors 27.5% (iid: 91.9%), P(null >= 32) = 0.031. The screen still beats chance, but the evidence is about 60 times weaker than stated — add a declared block or circular-shift permutation as a labelled sensitivity analysis and drop "decisive" / "cannot be argued with" (M).
- [P1] The bootstrap intervals treat autocorrelated, clustered holdout failures as independent — yield_screening/modeling.py:140-168 (PR-AUC) and yield_screening/screening.py:87-122 (holdout rank-biserial) both draw iid stratified resamples. By auditor computation, 15 of the 26 holdout failures fall in a single week (2008-09-29 to 10-05). README.md:52-54 says the intervals "are wide because 26 holdout failures cannot support anything narrower", but iid resampling likely makes them too narrow. The headline statements "Both intervals exclude zero" (README.md:52) and "The interval contains the floor" rest on this — report a day- or week-block bootstrap alongside, as a labelled sensitivity analysis, without replacing the frozen D10 numbers (M).
- [P1] (factual) "Before any holdout record was read" is contradicted by the Gate 1 documents themselves — DECISIONS.md:15-17 and README.md:212-213 make the claim. Yet the same Phase 1 commit contains the monthly failure rates for Sep and Oct 2008, i.e. the holdout period (DECISIONS.md:36-43), the holdout fail count and rate (DECISIONS.md:60-61: 26 fails, 0.0552), the holdout positive rate used for the no-skill line (DECISIONS.md:394-395), and the holdout fails table in reports/data_quality.md:189-201 (be5c440). Holdout label aggregates were read before the freeze. No holdout feature-label association was computed, so the leakage impact is low, but the absolute claim is false — reword to "before any holdout feature/label association was computed" (S).
- [P1] (factual) The tests were not written in the phase the docs claim — PLAN.md:59-66 and README.md:341-342 ("each written in the phase that produced the code it covers") conflict with git. `tests/test_split_and_fitscope.py` (temporal and fit-scope tests, scheduled for phase 2) first appears in f5b3e21 (Phase 3), after the Phase 2 screen results and in the same commit as the first holdout read. `tests/test_screening_synthetic.py` (planted signal and FDR, phase 2) first appears in b7161cf (Phase 4). `tests/test_determinism.py` (phase 4) appears in de41ce2, after the Phase 4 results. Only the supporting test_screening_math.py shipped with Phase 2 — correct the text (S).
- [P1] The git history cannot demonstrate plan-before-results — `git log` shows all 14 commits on 2026-08-23. Three of them fall within one second (05204ea 03:34:40, dd1f1e4 03:34:41, be5c440 03:34:41), together adding more than 2,000 lines including the 575-line DECISIONS.md and the 461-line QA script. The scaffold README (05204ea) already cites DECISIONS.md one second before that file exists. The full screen with BH and a 2000-permutation null follows 10 minutes later (2022c94), and Phases 1-5 span 54 minutes. The "FROZEN at Gate 1, approved by the owner" line (DECISIONS.md:15-17) was added in 2022c94, the same commit as reports/screening.md. No tag, PR or review marks Gate 1, so README.md:206-207 ("frozen at an owner approved gate") is unverifiable. Commit order is consistent with the claimed sequence, but a bulk-committed history is evidence of order only, not of timing — say this plainly in README and DECISIONS. In future work, tag or push each gate before running the next phase (S).
- [P1] Unpinned deps and no declared Python version mean the committed artifacts are not byte-reproducible outside the author's environment — requirements.txt:1-16 uses only `>=` pins, there is no lockfile or pyproject, and Python 3.11 appears only in .github/workflows/ci.yml:15. On my fresh install every reports/*.md regenerated byte-identically, but four artifacts changed: reports/screening_table.csv:55 and dashboard/model_data.json:794 differ in the last floating-point digit; the "ten worst sensors" table at reports/data_quality.md:67-76 reorders and swaps sensor_244 for sensor_518 (a non-stable sort on tied missing rates at scripts/run_data_qa.py:633); and dashboard/index.html now embeds plotly.js v4.1.1 instead of v3.7.0. This contradicts README.md:268 ("byte identical reports") beyond one environment — pin exact versions or add a lockfile, declare `python_requires`, and use `kind="stable"` plus a name tie-break at run_data_qa.py:633 (S).
- [P1] (factual) README finding 4 overstates a null result — README.md:90-91 says "Out of control records fail no more often than in control records, at every severity threshold". The sweep shows higher flagged fail rates at several thresholds: k=2 5.70% vs 4.00%, k=5 7.56% vs 4.83%, rule 1 k=1 6.67% vs 5.30%, and rule 1 k=2 12.5% vs 5.40% (reports/spc.md:98,101,107,108). What the data support is "no detectable difference" — reword to "no threshold shows a statistically detectable difference (smallest BH-adjusted p = 1.000)" (S).
